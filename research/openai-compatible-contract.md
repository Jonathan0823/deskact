# OpenAI-compatible endpoint contract for structured agent plans

**Context:** [Wayfinder research issue #4](https://github.com/Jonathan0823/deskact/issues/4) asks which endpoint features DeskAct can reasonably rely on and which require provider/model-specific handling. This is evidence for a human decision, not a policy recommendation.

**Scope and method:** Primary sources only: official OpenAI API documentation and first-party documentation from Ollama, vLLM, and LM Studio. Documentation describes advertised behavior; it does not establish cross-provider conformance or model-level reliability. Findings reflect documentation available on 4 November 2026.

## Executive answer

“OpenAI-compatible” identifies a useful request/response convention, not a guarantee that every OpenAI endpoint, parameter, schema feature, or model behavior is implemented. The clearest common denominator across these representative providers is **Chat Completions-style messages and a completion response**; even that varies in accepted fields, model/template prerequisites, and semantics. JSON Schema-constrained output, tool calling, streaming, and model listing are implemented by multiple providers, but support is conditional, differently exposed, or absent in documented provider modes. [OpenAI API reference](https://platform.openai.com/docs/api-reference/chat); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility); [vLLM compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/); [LM Studio endpoints](https://lmstudio.ai/docs/developer/openai-compat)

No endpoint feature should be treated as evidence that a generated plan is safe or correct. A client can validate response structure and action arguments locally, but must still apply DeskAct policy and verify outcomes. Model/provider support, refusal/truncation behavior, and stream/tool edge cases need empirical tests against declared endpoint + model + server-version combinations. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); [OpenAI streaming reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)

## Findings

### 1. API shape and compatibility

- OpenAI publishes a Chat Completions interface with messages and structured completion responses; providers intentionally target portions of this interface. Ollama explicitly calls its implementation a **subset**. Its local OpenAI-compatible server documents `/v1/chat/completions`, `/v1/completions`, `/v1/models`, embeddings, and additional endpoints, while its cloud offering has different limitations. [OpenAI Chat API](https://platform.openai.com/docs/api-reference/chat); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)
- vLLM advertises Chat Completions and Completions plus Responses and other endpoints. Its documentation notes conditions (for example, chat requires a compatible chat template), ignored or model-dependent fields, and vLLM-specific extra parameters. LM Studio documents `/v1/chat/completions`, `/v1/responses`, and other endpoints; it also exposes non-OpenAI extensions such as `/v1/decisions`. Hence the common client convention does not imply identical API surface or semantics. [vLLM compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/); [LM Studio endpoints](https://lmstudio.ai/docs/developer/openai-compat)
- Provider/model identity and deployment mode matter. Ollama's cloud supports only stateless Responses and explicitly excludes stateful Responses, built-in web search through Responses, and custom/freeform tool-call replay; local has separate docs and behavior. Base URL, endpoint, model identifier, and deployment mode must therefore be treated as configuration, not inferred from the label “OpenAI-compatible.” [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)

### 2. JSON and JSON Schema structured output

- OpenAI distinguishes **JSON mode** (valid JSON, no schema adherence) from **Structured Outputs** (schema-constrained response on supported models). Its docs say Structured Outputs is model-dependent, recommend it over JSON mode where possible, and document schema restrictions and refusal/unfinished-response handling. Thus even the reference API does not equate a JSON request with guaranteed schema conformance for every model. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- Ollama's local native API accepts either `format: "json"` or a JSON Schema in `format`; its OpenAI-compatible Chat Completions support is documented as JSON mode through `response_format`. Crucially, Ollama states its **cloud currently does not support structured outputs**. Its local API docs recommend including the schema in the prompt and validating parsed output. [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)
- vLLM supports `response_format` JSON Schema/JSON object and has its own `structured_outputs` request extension, with multiple constraint backends (e.g. XGrammar/Guidance). Its docs warn that backend syntax/support can differ; deprecated and renamed fields also demonstrate version sensitivity. [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/); [vLLM compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)
- LM Studio documents `response_format` with a JSON Schema on Chat Completions and says the response appears as JSON text in `choices[0].message.content`; it expressly warns that not all models, particularly smaller ones, are capable of structured output. Its enforcement engine also differs by model file format (GGUF grammar sampling, MLX Outlines). [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)
- **Variability:** field placement and semantics are not uniform: OpenAI uses `response_format` / API-specific text format; Ollama native API uses `format` and its OpenAI-compatible interface advertises JSON mode; vLLM accepts standard-looking response formats but also supports extensions; LM Studio uses Chat Completions `response_format`. Schema subset support, strictness, model ability, refusal signaling, and behavior on invalid/unsupported schema all remain endpoint/model-specific. [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs); [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/); [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)

### 3. Tool/function calling

- OpenAI documents function tools as JSON-Schema-described requests from the model to the application. The application—not the model service—executes functions and returns their results in a follow-up turn. OpenAI recommends strict mode but documents schema restrictions; calls may be streamed as partial name/argument data, and arguments require application-side handling. [OpenAI function calling](https://developers.openai.com/API/docs/guides/function-calling); [OpenAI streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events)
- Ollama documents function/tool calling, including single and multiple calls, on its local API; the OpenAI-compatible endpoint lists tools and tool choice as supported fields. Calls are still a model-produced request to the client, not execution by Ollama. Its cloud feature limitations make it unsafe to assume every tool-flow variant works across Ollama modes. [Ollama tool calling](https://docs.ollama.com/capabilities/tool-calling); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)
- vLLM supports Chat Completions tools; whether parallel calls occur is model-dependent, and `parallel_tool_calls=false` can constrain output to zero or one call. Its endpoint support and model/template prerequisites still apply. [vLLM compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)
- LM Studio supports tools on Chat Completions and Responses. It distinguishes native model/template tool support from a default prompt-and-parser fallback; it warns that smaller or untrained models may emit malformed calls that are returned as ordinary text instead of `tool_calls`. [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)
- **Safety implication:** a tool call is a proposed action with untrusted arguments, not authorization. Validate the call identifier/name/argument object, reject unknown tools and invalid arguments, enforce app-side allowlists and approval policy, and do not execute a partial streamed call. This follows the documented client-side execution flow and the documented possibility of malformed/nonconforming arguments. [OpenAI function calling](https://developers.openai.com/API/docs/guides/function-calling); [OpenAI streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)

### 4. Streaming

- Streaming over Chat Completions is an established convention: OpenAI documents server-sent event chunks and `stream=true`. Ollama lists streaming for its OpenAI-compatible chat endpoint, vLLM implements Chat Completions, and LM Studio documents streamed content and tool-call deltas. [OpenAI streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)
- The **wire-level event details and availability are not universal**. OpenAI's Responses API has typed events; Chat Completions uses chunk objects/SSE. LM Studio says tool names and arguments arrive piecewise and need aggregation. Ollama SDK streaming defaults differ from REST behavior, and vLLM's support is tied to its server/API implementation. [OpenAI Responses streaming](https://developers.openai.com/api/docs/guides/streaming-responses); [OpenAI Chat streaming](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [Ollama streaming](https://docs.ollama.com/capabilities/streaming); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)
- A stream is incomplete until its terminal event/finish reason is received; interruptions may omit final usage data. Do not parse/execute an unfinished JSON response or tool call. Non-streaming requests are a documented alternative across the endpoint examples and simplify assembling a complete plan, while streaming can remain an optional presentation/latency feature. [OpenAI Chat streaming](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)

### 5. Model discovery

- `/v1/models` is a common OpenAI-style discovery route, but availability and meaning vary. Ollama documents it in its compatibility endpoint list and separately provides local `/api/tags` with local model metadata. LM Studio documents `GET /v1/models`, returning models visible to the server (which may include downloaded models when just-in-time loading is enabled). vLLM's structured-output example discovers a served model using `client.models.list()`. [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility); [Ollama list models](https://docs.ollama.com/api/tags); [LM Studio models](https://lmstudio.ai/docs/developer/openai-compat/models); [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/)
- Discovery does not establish capability. A listed identifier does not certify JSON Schema support, tool competence, chat-template availability, context limit, or support for a particular request field. LM Studio's model-card guidance and native/default tool distinction, and vLLM's chat-template prerequisite, show why capability should be probed/tested rather than assumed from listing alone. [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools); [vLLM compatible server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/)

### 6. Safe fallback patterns evidenced by the docs

These are implementation options supported by provider documentation, not a selection of DeskAct policy:

1. **Validate locally regardless.** Parse complete response content, validate it against DeskAct's own schema and semantic invariants, and treat refusals, truncation, missing content, parse failures, and invalid fields as non-plans. OpenAI explicitly distinguishes JSON validity from schema adherence and provides refusal signaling; Ollama recommends validation. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)
2. **Use narrow schema/feature profiles.** Keep schemas within a tested subset and probe support for the configured provider/model; do not silently downgrade from schema-constrained output to unconstrained prose while continuing execution. Provider docs demonstrate both model-specific support and backend-specific constraints. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); [vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/); [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)
3. **If structured-output request is unsupported:** fail closed for execution or return to a non-executing user clarification/manual path. A separate best-effort JSON/prompting retry could be experimentally evaluated, but must still pass the same local validator and cannot inherit a guarantee from a provider's structured-output feature. OpenAI explicitly says JSON mode alone does not guarantee schema adherence; Ollama's local docs suggest prompt grounding alongside schema; LM Studio documents model ability variation. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs); [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output)
4. **If tool calling is absent/unreliable:** do not treat text that resembles a tool call as an actual invocation. Could instead request a complete plan as schema-constrained data and let the Rust orchestrator interpret only known typed actions; this still requires local validation, policy gating, approvals, and outcome verification. LM Studio expressly notes malformed text may remain in message content rather than the `tool_calls` field. [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools); [OpenAI function calling](https://developers.openai.com/API/docs/guides/function-calling)
5. **If streaming is unavailable or interrupted:** use a non-streaming completion or discard the incomplete result and make a bounded new request only under an application-defined retry policy. Never execute until a complete response has been assembled and validated. [OpenAI Chat streaming](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)
6. **If discovery is unavailable/unhelpful:** allow explicit model identifier configuration and test the configured model directly; model listing is a discovery convenience, not a capability contract. [LM Studio models](https://lmstudio.ai/docs/developer/openai-compat/models); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility)

## Common conventions vs. provider-specific behavior

| Area | Convention appearing across sources | Documented differences/extensions |
|---|---|---|
| Endpoint | OpenAI-shaped `/v1/chat/completions` and JSON request/response conventions | API subset, endpoint inventory, field support, auth and model/template requirements vary; Ollama cloud differs from local; vLLM and LM Studio expose extensions. |
| Structured output | JSON and JSON Schema are broadly used concepts | `response_format` vs `format` vs vLLM `structured_outputs`; actual schema enforcement is model-, server-, and mode-dependent. Ollama cloud explicitly lacks it. |
| Tool calling | Function name + arguments described by schema; client handles execution and results | Tool parser/template/model quality, strictness, parallel calls, replay format, and cloud/local availability differ. LM Studio's fallback parser is especially explicit. |
| Streaming | `stream=true` and incremental output are common | Event envelopes and partial tool-call behavior differ; consumer must assemble and detect completion. |
| Model discovery | `/v1/models` appears in several implementations | Listing contents and whether it means installed, visible, loaded, or served models differ; listing is not a feature-capability declaration. |

Sources: [OpenAI API reference](https://platform.openai.com/docs/api-reference/chat); [Ollama compatibility](https://docs.ollama.com/api/openai-compatibility); [Ollama model listing](https://docs.ollama.com/api/tags); [vLLM server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/); [LM Studio endpoints](https://lmstudio.ai/docs/developer/openai-compat)

## Facts still requiring empirical tests

Documentation alone cannot establish reliable behavior for DeskAct's actual combination of server build, model identifier/revision, quantization, template, and request schema. A compatibility suite should test, at minimum:

- Required/optional/null fields, enums, nested arrays/objects, unknown keys, and unsupported schema keywords; assert both JSON parsing and DeskAct-side semantic validation.
- Normal completion, refusal, empty response, truncation/length finish, timeout, malformed JSON, and retry behavior.
- Tool-call choice, malformed/unknown tool name, missing/extra/ill-typed arguments, multiple calls, tool-result round trip, and non-call text that resembles a call.
- Stream chunk aggregation, interleaved content and tool deltas, cancellation/disconnect, terminal finish reason, and ensuring no partial call executes.
- Model discovery against no models, multiple models, loaded/unloaded/JIT models, aliases, and invalid model identifiers.
- Endpoint and auth differences across local vs remote deployments, including Ollama cloud vs local if both are in scope.

These are test targets, not claims that every provider exhibits each failure. Primary documentation establishes concrete variability—for example model/template prerequisites, differing output-format fields, cloud limitations, partial streamed arguments, and model-dependent tool-call capability—but does not provide a conformance guarantee for the DeskAct action-plan schema. [OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs); [OpenAI function calling](https://developers.openai.com/API/docs/guides/function-calling); [OpenAI streaming events](https://developers.openai.com/api/reference/resources/chat/subresources/completions/streaming-events); [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs); [vLLM server](https://docs.vllm.ai/en/stable/serving/online_serving/openai_compatible_server/); [LM Studio structured output](https://lmstudio.ai/docs/developer/openai-compat/structured-output); [LM Studio tool use](https://lmstudio.ai/docs/developer/openai-compat/tools)

## Open decision for DeskAct

This survey does **not** decide whether DeskAct should require JSON Schema output, tool calling, streaming, or model discovery. It establishes that endpoint compatibility cannot make those features uniform guarantees. The human decision can weigh a narrower tested endpoint contract against wider compatibility with validation and non-executing fallback paths; whichever route is chosen, all model-proposed actions remain subject to Rust-side validation, policy, approval, and observe/verify behavior.
